Insights Quick Guide (How To Read This Panel)
  1. Start with Workload Impact: shapes ranked by summed concurrent operation time across every completed operation, including fast ones. It is not wall-clock or CPU time, and it does not say why a shape is expensive.
  2. Use Top Findings to identify the highest-impact and highest-severity shapes.
  3. Use Affected Collections, Iterations, and Timeline for scope and drift context.
  4. Open the Query & Index Analysis tab for per-query efficiency, slow queries, explain results, index issues, and recommended actions. Most of that tab requires Post-Run Explain Sampling (settings tab Query Analysis (Explain)), which is on by default.

Query & Index Analysis Quick Guide

Requires Post-Run Explain Sampling. Scan efficiency, execution overhead, sort and spill measurements, plan-based index recommendations, and efficiency trends come from explain output collected after the workload finishes. The setting is on the Query Analysis (Explain) settings tab and is on by default. If it is off, this tab reports only latency and workload impact, and the remaining columns show as unassessed or not measured.

  1. Open Efficiency to find shapes that examine many more documents or index keys than they return, including fast ones. Scan efficiency, query latency, workload impact, execution overhead (in-memory sorts, disk spills), and $lookup/lock/network measurements each have their own column; each column's explanation is shown above the table.
  2. Open Slow Queries & Indexes and prioritize high p95/p99 with high count.
  3. Check Explain status and reason to see if guidance is explain-backed or heuristic.
  4. Use Potential Index Issues confidence and evidence level, then Recommended Actions, to rank remediation work.
  5. Open Trends to compare each shape with its stored baseline from earlier runs. Efficiency, latency, and impact are compared separately; a shape is labeled improved or regressed only when the baseline is compatible and both runs meet the published evidence minimums. Annotations such as a plan or index change are not evidence of cause.
Replay Comparison
Compare the outcome files of two executions of the same operations: two replays of one recording, a recording with outcomes and a replay of it, or two deterministic runs with the same traffic fingerprint. Operations are matched one to one (by recording seq, or by iteration, worker, and per-worker seq). Result and error differences are facts; latency verdicts are heuristics. Files with a different recording or fingerprint are refused unless you allow the mismatch.

Workload Control

Defines the worker count, how that count is shaped over time, and how long the run lasts. The load profile is the single source of truth for concurrency.
Worker count is controlled by the load profile fields below; this value is used only as a fallback.
Total run length per iteration. Load-profile timings (ramp, step, spike, period) happen inside this window, so each should be shorter.
Period is the length of one full oscillation (Min → Max → Min), not the run length. Keep Period ≤ Duration; for whole cycles, make Duration a multiple of Period (e.g. 120s ÷ 30s = 4 waves).

Iterations

Repeat the whole workload, with an optional pause between runs.

Emulate realistic client behavior with per-operation pacing and skew which records are accessed. Defaults preserve no-pacing, uniform behavior.

Access Pattern

Reproducible Workload (Record & Replay)

Run the exact same operations, with the same values, on two instances: record on one, replay on the other. Off by default. Record and replay cannot both be on for the same run, and neither works with the raw injector.
Record, then replay
Record a run on the source instance, then replay the file on one or more target instances.
Deterministic generation
Generate identical traffic from the same random seed on every instance, without a recording file.
Import captured traffic
Convert mongod logs or profiler exports into a recording, then replay it like any other.

Seed & Deterministic Traffic

Make generated data and operations repeatable. With deterministic traffic, every instance receives the same commands without a recording file.
Any run
Set (non-zero): seeds data and query generation, so the same seed, documents count, and collection definitions seed identical documents on any instance; use it on both sides of a replay. 0 (default): values are time-based and differ every run. random_seed / PLGM_RANDOM_SEED
On: every operation is generated from the random seed, iteration, worker, and operation number, so two runs with the same settings send the same commands with the same values, without a recording file. Each worker sends exactly Operations per Worker operations; failures and retries do not shift later operations. Needs a non-zero Random Seed, Drop Collections on and Skip Seed off, and a fixed worker count; Duration becomes a safety timeout (the run is marked incomplete if it is hit). The insert cache and bootstrap are not used, and the run reports a traffic fingerprint (hashes only). Cross-worker interleaving, server-generated values, and results on different data can still differ. Off (default): operations are generated as usual until Duration ends. workload_deterministic / PLGM_WORKLOAD_DETERMINISTIC
Set: each worker sends exactly this many operations per iteration; required when Deterministic traffic is on. 0 (default): no operation budget; workers run until Duration ends. operations_per_worker / PLGM_OPERATIONS_PER_WORKER

Record

Write every operation this run sends, with its exact values, to a recording file that can be replayed elsewhere.
Source instance
On: writes every operation sent, with its exact values, to the recording file so it can be replayed on another instance. The file contains real query values, and recording adds about 2 µs per operation. Every iteration is recorded into the one file, and a replay runs them in order. Off (default): nothing is recorded. workload_record_enabled / PLGM_WORKLOAD_RECORD_ENABLED
Set: NDJSON file on the server, written with mode 0600; an existing file that is not a recording is never overwritten. Empty (default): plgm_workload_record.ndjson in the working directory when recording is on. workload_record_path / PLGM_WORKLOAD_RECORD_PATH
Set: when the uncompressed size reaches this many bytes the recording stops and is marked truncated; the run continues. 0: unlimited; watch the free disk space. Empty (default): 536870912 (512 MiB). workload_record_max_bytes / PLGM_WORKLOAD_RECORD_MAX_BYTES
Block: workers wait for the writer, so every operation is recorded; throughput may drop, and the total and longest wait are reported. Fail (default): the recording stops and is marked failed; the run continues at full speed. workload_record_backpressure / PLGM_WORKLOAD_RECORD_BACKPRESSURE
zstd / gzip: compresses the file (typically 10–15× smaller; zstd is faster) at some extra writer CPU; replay and upload detect it. The size cap counts uncompressed bytes. None (default): plain NDJSON. workload_record_compression / PLGM_WORKLOAD_RECORD_COMPRESSION

Replay

Run the operations from a recording instead of generating new ones.
Target instance
On: no operations are generated; the recorded operations run on the recorded worker count until the file ends. Duration, load profile, access pattern, and think time are ignored. Iterations is ignored too: the replay runs once and replays every recorded iteration in order. Off (default): operations are generated as usual. workload_replay_enabled / PLGM_WORKLOAD_REPLAY_ENABLED
Set: the recording to replay; an uploaded file is used instead of the path and deleted after the run. Empty (default): nothing to replay; required when Replay Workload is on. workload_replay_path / PLGM_WORKLOAD_REPLAY_PATH
Timed: sends each operation at its recorded offset from the start and reports how far behind it fell (lag). Per worker (default): each worker sends its recorded operations in order, as fast as possible. workload_replay_mode / PLGM_WORKLOAD_REPLAY_MODE
Reads only: replays finds and read-only aggregates and skips every write (inserts, updates, deletes, transactions with a write, and aggregates with $out or $merge), so the target keeps its starting data; skipped writes are counted and reported, and the commands hash is not compared. All (default): replays every recorded operation, including writes. workload_replay_ops / PLGM_WORKLOAD_REPLAY_OPS
On: replays even when the collection/query definitions or namespaces differ from the recording, or the recording did not complete; results may not be comparable. Off (default): such a replay fails before any operation is sent. workload_replay_allow_mismatch / PLGM_WORKLOAD_REPLAY_ALLOW_MISMATCH

Multi-Target Replay & Starting Data

Replay one recording on several instances and check that each one starts from the same data.
2–8 targets
Listed (2–8 targets): the replay (or deterministic run) runs once on every listed target, and only on those: MongoDB URI is not used. Each target gets its own client, workers, stats, outcome file (the label goes before the extension, for example outcomes.m8.ndjson), insights, and trend run, and is compared with the first target. Needs Replay Workload or Deterministic traffic, and Record Outcomes with an outcome file. Username, password, and TLS settings apply to every target; put other per-target options in its URI. Empty (default): a single run on MongoDB URI. workload_replay_targets / PLGM_WORKLOAD_REPLAY_TARGETS (label=uri;label=uri)
Concurrent: every target is prepared first, one at a time, then all run at once from this host; they share its CPU, memory, and network, so latencies may be affected, and the report shows each target's client-side lag behind the recorded timeline. Sequential (default): targets run one after another and do not compete for this host. workload_replay_targets_mode / PLGM_WORKLOAD_REPLAY_TARGETS_MODE
Counts / dbHash: a recording stores each collection's document count and index list (plus the dbHash collection hash with dbHash) before the first operation; every replay of it compares them with its target first and fails on a difference (warns with Allow Mismatch). dbHash needs the dbHash privilege, does not run through mongos, and matches only byte-identical copies (a snapshot or mongodump restore), not separately seeded ones. A replay always checks a recording that has a fingerprint. Off (default): nothing is stored or checked. workload_data_fingerprint / PLGM_WORKLOAD_DATA_FINGERPRINT

Outcome Capture

Keep what every operation returned so two executions can be compared operation by operation (Query Analysis > Replay Comparison).
Result comparison
On: keeps what every operation returned: client latency, ok or the error code and name (never the message), and a result summary (documents returned; inserted; matched/modified/upserted; deleted; transaction commit/abort), so two executions can be compared. A recording stores it on each operation line; a replay or deterministic run writes it to the outcome file below. The commands sent, stats, insights, and trends do not change; the cost is negligible without checksums. Off (default): no outcomes are kept and recordings are unchanged. workload_record_outcomes / PLGM_WORKLOAD_RECORD_OUTCOMES
On: adds an order-sensitive sha256 of every find and aggregate result (each returned document as canonical Extended JSON, keys sorted) to its outcome, so different results show up even when the counts match. Costs about 5 µs of worker CPU and a copy of each returned document (hashed after the latency is measured); needs Record Outcomes on. Off (default): outcomes carry document counts only. workload_record_result_checksums / PLGM_WORKLOAD_RECORD_RESULT_CHECKSUMS
Set: a replay writes one outcome per replayed operation to this NDJSON file (mode 0600), with the recording's sequence numbers and header hash, so any two executions of a recording can be compared offline; required when Record Outcomes is on during a replay. An existing file that is not an outcome file is never overwritten. Empty (default): a replay writes no outcome file. workload_replay_outcomes_path / PLGM_WORKLOAD_REPLAY_OUTCOMES_PATH
Set: a deterministic run writes one outcome per operation to this NDJSON file (mode 0600), keyed by iteration, worker, and operation number and stamped with the traffic fingerprint. Empty (default): no outcome file; with Record Workload on, the outcomes go into the recording instead. workload_deterministic_outcomes_path / PLGM_WORKLOAD_DETERMINISTIC_OUTCOMES_PATH

Import Captured Traffic

Converts real application traffic into a recording that Replay Workload runs, like pt-upgrade replaying logs. Nothing is imported until you click Convert; the same conversion runs from the CLI as plgm import-traffic.

Sources
mongod JSON logs (4.4+), a mongoexport of system.profile (NDJSON or --jsonArray), or raw command documents; plain, gzip, or zstd.
Conversion
Operations keep their order and timing (start = logged time minus duration), and each connection becomes a worker. find, aggregate, insert, update, and delete are converted; getMore, truncated commands, other commands, replacement updates, and system namespaces are skipped and counted.
Coverage
Logs and the profiler hold only operations slower than slowms (default 100 ms), sampled by slowOpSampleRate, unless profiling level 2 or slowms 0 was set while capturing.
Data handling
The recording contains literal values from the captured traffic; the server keeps the newest 5 (mode 0600) and deletes them when it shuts down from the UI.
Standalone tool
Chosen: every file is read, and their operations are merged in start-time order. None (default): nothing to convert.
Set: the captured connections are mapped onto this many workers, so several connections can share one worker and run one after another. 0 (default): one worker per captured connection, up to 1024.
Set: the database of raw command documents without $db. Empty (default): such commands are skipped and counted; log and profiler entries name their database.
zstd / gzip: the recording is compressed; replay detects it. None (default): plain NDJSON.
On: operations whose values the server generates (inserts or upserts without _id, $currentDate, $$NOW, $rand, $sample) are skipped and counted. Off (default): they are converted and flagged; their results can differ between targets.

Post-Run Explain

Explain is off. Scan efficiency, execution overhead, plan-based index recommendations, and efficiency trends will not be available for this run.
Recommended: keep on.

What it does. While the workload runs, PLGM keeps a few real example queries for each query shape. After the workload finishes, it sends a small number of them back to MongoDB as explain commands. The explain output shows how the server actually ran each query: which index it used (or a collection scan), how many index keys and documents it examined for the documents it returned, and whether it sorted in memory or spilled to disk. PLGM also reads the collection's existing indexes with listIndexes.

What you get. The Query & Index Analysis tab uses this output for:

  • scan efficiency ratings (0–100) that compare work examined with results returned, including for fast queries;
  • execution overhead: in-memory sorts, disk spills, and per-sample sort/spill measurements;
  • plan-based index recommendations with ordered candidate keys, checked against the indexes that already exist;
  • efficiency trends compared with earlier runs.

With it off, Query & Index Analysis reports only latency and workload impact, and the other columns show as unassessed.

Cost and safety.

  • Explain runs only after the workload finishes, never during the measured window, so benchmark results are not affected.
  • It is bounded: at most 2 × Top N query shapes, 2 samples each (20 explain commands with the defaults), one at a time by default, each capped by Explain Max Time, plus one listIndexes per explained collection.
  • Updates, deletes, and $out/$merge pipelines are explained without being applied; no data is changed.
  • During the run, keeping example queries adds well under 100 ns per operation.

Turn it off only if the cluster must receive no commands beyond the workload, or the connecting user is not allowed to run explain or listIndexes. It also needs Enable Post-Run Insights Analysis (Metrics & Insights tab).

Which Queries Are Explained

Explain slots come in two groups of Top N shapes each. Severity slots take the slowest shapes that pass the slow threshold and severity mode. Efficiency slots take shapes from the whole workload, alternating the highest workload impact with a spread across latency levels, so fast queries that scan too much are also found. Shapes that are not explained have no scan efficiency score; they are never shown as efficient.
Shapes per slot group. The default of 5 explains up to 10 shapes.
Default keeps explain focused on high-severity slow groups to reduce low-value attempts and timeout pressure.
Adds Top N explain slots chosen from every shape regardless of the slow threshold or severity mode, so fast shapes can be assessed.

Explain Execution Limits

How each explain command is run against the cluster after the workload. A timed-out or failed explain is reported as inconclusive, never as a finding.
executionStats runs the query plan and reports keys and documents examined, which scan efficiency and sort/spill measurements need. queryPlanner only shows the chosen plan, so most results are partial.

Query Latency Targets

Optional targets for the query latency rating in Query & Index Analysis. They apply to every query shape and do not need explain. Leave empty for no target; with no target, latency is shown but not rated.
